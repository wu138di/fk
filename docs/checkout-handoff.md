# 官方付款链接交接：待接入设计

状态：仅完成价格展示修改和代码审查，下面是接入方案，不是已部署功能。

用户确认所指为官方付款链接 / Checkout 会话 ID，不涉及账号登录 Access Token。

## 目标流程

买家在本站支付 135 元 → 提交完整官方付款链接 → 后台生成待处理工单 → 管理员在官方收银台手动支付 → 管理员确认交付。

本站收款与外部订阅付款是两笔不同交易。本站收款成功不代表外部充值已完成。系统不自动替管理员付款，也不采集银行卡、账号密码、登录令牌或验证码。

## 当前仓库可复用的点

- `OrderProcessService::completedOrder()` 在核对金额、处理订单并提交事务后，派发 `ApiHook`。
- `GoodsController` 支持 `api_hook` 和 `other_ipu_cnf` 配置。
- `OrderService::validatorChargeInput()` 把扩展字段明文拼接到订单信息；`ApiHook` 会转发订单信息。因此不要直接把完整付款链接填进普通备注/扩展字段。
- 现有 ApiHook 未提供回调签名和完善的交付幂等保证，不能单凭收到一个 POST 就认可收款成功。接入时应从本站数据库重新核验付款状态，新增独立交接任务，并用唯一订单约束防重。

## 建议新增

1. **已付款订单提交入口**：使用现有订单归属证明，并加 CSRF、限流；只允许订单本人提交。不使用“订单号 + 邮箱”作为唯一身份依据。
2. **独立交接表**：订单 ID 唯一、加密付款链接、可选会话 ID、状态、失效时间、操作者、确认交付时间。普通查单只返回状态，不返回完整链接。
3. **链接校验**：仅 HTTPS、精确匹配经确认的官方收银台域名、拒绝 userinfo 和非标准端口。不由服务器请求用户 URL，不跟随重定向。
4. **管理端**：限定管理员权限查看链接；新窗口 `noopener noreferrer`，设置 `Referrer-Policy: no-referrer`。通知中只含订单号和后台入口，不含链接或会话值。
5. **生命周期**：提交 → 待处理 → 处理中 → 已交付 / 已失效。并发领取加锁，过期重新提交，交付后清除原始链接。日志不记录链接、查询参数或 token。
6. **支付行为**：管理员自行在官方收银台核对商品、金额、币种与账号，再手动支付。不能由“打开了链接”或买家提供的截图自动推断已付款。

## 会话 ID 与完整链接

以 Stripe Checkout 为例，Session 对象的 `id`、`url`、`expires_at` 是不同字段；ID 不是完整付款链接。优先提交完整官方 `url`，不要根据 ID 拼接猜测链接。仅有 ID 时，需要该会话所属商户的适当权限来查询 URL，本站凭自己的密钥不代表能读取其他商户的会话。

资料：https://docs.stripe.com/api/checkout/sessions/object

用户进一步要求：买家自行复制带账号信息的 token，并由管理员付款。FANBOX 的具体复制入口、字段名称和 token 权限尚未确定，因此暂未创建 token 收集或复用功能。

## FANBOX 官方资料核查（2026-10-07）

- 官方帮助列出 PayPal、信用卡、pixivcoban 与便利店支付；资料中没有找到“用户导出通用支付 token，第三方据此读取账号并付款”的公开接入说明。这是检索结果，不是证明平台内部不存在相关字段。
- 便利店流程明确提到按交易确定邮件中的步骤付款，存在支付期限，逾期交易自动取消。尚未验证其凭证是否允许转交第三方，也未确认能在用户所在地区完成付款。
- 参考资料：
  - https://fanbox.pixiv.help/hc/zh-cn/articles/360003698754
  - https://fanbox.pixiv.help/hc/zh-cn/articles/360013905413
- 待用户提供复制入口的脱敏截图或接口字段说明，不能将登录 Session / Cookie 误称为仅限一笔交易的支付 token。
- 所需账号信息可以使用公开用户 ID / 主页链接，加创作者链接、方案、金额进行订单匹配；这些信息不代表已验证账号归属。
- 没有已确认的上游接口时，不预设或调用第三方内部支付接口。
